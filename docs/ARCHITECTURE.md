# Architecture

Personal Finance Tracker: Qt 6 · C++20 · QML · SQLite · CMake, targeting iOS
(Xcode project generated by CMake). All data stays on the device.

## 1. Environment findings (the "First Task")

Inspected in the development sandbox:

| Item | Finding |
|---|---|
| OS | Ubuntu 24.04 (Linux). **No macOS, no Xcode, no iOS SDK, no `xcodebuild`** |
| Compiler / CMake | GCC 13.3, CMake 3.28.3 |
| Qt | 6.4.2 from apt (Core, Gui, Qml, Quick, QuickControls2, Sql + SQLite driver, Test, Concurrent). No iOS kit |
| Rendering for visual checks | Xvfb + Mesa llvmpipe (OpenGL RHI) works; the Qt Quick *software* backend does not draw `Shape` layers |

Consequences:

* Desktop (Linux) builds, unit tests and headless UI screenshots are possible
  and are how everything here was verified.
* **The iOS build cannot be produced or tested in this environment.** iOS
  specifics (`IOSPlatform.mm`, `Info.plist.in`, Xcode/signing properties) are
  written against Apple/Qt documentation but are unexecuted. See
  [BUILD_IOS.md](BUILD_IOS.md) for the Mac-side procedure (Qt 6.8 LTS iOS kit
  is recommended; 6.4.2 is only the desktop development version).

## 2. Layering

```
 QML (qml/)                presentation only, no business rules
   │  binds to
 App singleton  ────────   ApplicationManager (composition root, exposed to QML)
   │
 Services (src/services)   validation + use-cases, return Status/Result<T>
   │                       AccountService · TransactionService · AnalyticsService
   │                       SmsImportService (bank-SMS pipeline + QML facade)
 SMS layer (src/sms)       receivers · sanitizer · parsers · registry (see §9)
 Categorization            MerchantNormalizer · CategorizationService (rules)
 Repositories (src/database)  prepared statements, one class per aggregate
   │
 DatabaseManager           per-thread SQLite connections, WAL, migrations
 
 Models (src/models)       plain value types + QAbstractListModel subclasses
 Core (src/core)           Money, Currency, Result, SettingsManager, DemoData
 Platform (src/platform)   PlatformServices interface; Desktop stub / iOS (ObjC++)
```

* `pf_core` is a **static library with only QtCore + QtSql** (no QML/GUI). The
  app and the tests link the same library, so all logic is testable without a
  display.
* Dependencies point downward only. Services receive repositories by reference
  (constructor injection); nothing reaches for globals except the single `App`
  QML singleton, which is created in `main.cpp`.

### QML ↔ C++

* One singleton, `App`, registered with `qmlRegisterSingletonInstance`
  (`PersonalFinance.Core`). It owns the services and list models.
* Services expose **QVariantMap facades** to QML (`save(map)`,
  `deleteTransaction(id)`, …) returning `{ ok, error, id, duplicate }`.
  Validation lives in C++ (`validate`) and is also unit-tested.
* List data uses `QAbstractListModel` subclasses (`AccountListModel`,
  `CategoryListModel`, `TransactionListModel`). `TransactionListModel` pages with
  `canFetchMore/fetchMore`, supports search/type/account/category filters and
  coalesces reloads.
* Derived values (dashboard totals) re-evaluate through a `App.revision`
  counter bumped after every data change, which keeps QML bindings simple and
  avoids per-value change signals.

## 3. Money and data integrity

* Amounts are **`int64` minor units** plus an ISO 4217 currency code. No
  `double` is used for money anywhere. Exponents come from a currency registry
  (33 currencies; e.g. AMD 2, JPY 0).
* Arithmetic is exact and overflow-checked (`qAddOverflow` …). Mixing
  currencies is a programming error and aborts (`qFatal`); the Dashboard never
  sums across currencies because that would need exchange rates.
* Parsing user input is locale-aware (`1.234,56` vs `1,234.56`) and reports an
  `ambiguous` flag instead of guessing.
* Errors use `Status` / `Result<T>`; no exceptions cross layer boundaries.

## 4. Database

SQLite with `PRAGMA foreign_keys=ON`, WAL, busy timeout. Schema version is
tracked with `PRAGMA user_version`; migrations are in `Migrations.cpp`.

| Table | Purpose / notable constraints |
|---|---|
| `accounts` | bank, name, currency, card network, optional `last_four` (CHECK: exactly 4 digits), `initial_balance_minor`, archived |
| `transactions` | `amount_minor > 0` (sign comes from `type`), FK → accounts (CASCADE), categories (SET NULL), import_history; `fingerprint` (SHA‑256) for duplicates; `search_text` (normalized) for Unicode‑safe search |
| `categories` | 11 built‑ins seeded (Groceries … Cash, Other) + user categories |
| `budgets` | monthly or per‑category; expression UNIQUE index `(COALESCE(category_id,0), period, currency)` |
| `categorization_rules` | keyword/exact/regex rules with `priority` and `confidence`; ~110 starter rules (en/ru/hy, `is_system=1`) seeded by migration v2; user rules use priority 1000 |
| `sms_imports` (v2) | one row per SMS the import pipeline saw: status (`imported`, `needs_review`, `duplicate`, `ignored`, `unrecognized`, `rejected`), review reason, error code, bank/parser, **masked** text (empty for OTP/promotions/test), body hash, confidence, linked transaction, suggested category, reported balance, received/imported times. Unique partial index on the envelope id makes re-ingest idempotent |
| `import_history` | one row per import batch |
| `settings` | key/value (theme, language, default currency) |

* Only prepared statements with bound values; `LIKE` input is escaped.
* Writes run in `BEGIN IMMEDIATE` transactions that nest safely.
* Connections are **per thread** (`QThreadStorage`), so background work (future
  imports) never shares a connection with the UI thread. A test inserts from a
  worker thread.
* **Never stored:** full card numbers, CVV, PINs, banking passwords. The schema
  has no column for them, and `last_four` is CHECK-constrained.
  Account balance = initial balance + signed sum of its transactions, computed
  in SQL (no stored running balance to drift).

## 5. UI

* Qt Quick Controls with the **Basic** style (fully customizable and the same on
  every platform), custom design tokens in `qml/styles/Theme.qml` (a QML
  singleton): light/dark palettes, spacing, radii, stroke icons as SVG path
  strings drawn by `Icon.qml` with `QtQuick.Shapes`.
* Wallet/Revolut-style layout: bottom tab bar, hero balance card, bottom sheets
  (`SheetPopup`) for create/edit, wheel date picker, safe‑area aware via
  `App.platform.safeArea*`.
* Bottom sheets keep the primary action pinned below the scrolling form.
* Dark/light follows the system unless overridden in Settings.

## 7. Roadmap and design for the next phases

| Phase | Planned design |
|---|---|
| 2 – Parsing & import | `IBankParser` (`canParse(text) → confidence`, `parse(text) → ParsedTransaction`) with a `ParserRegistry` configured from data, not a hardcoded bank list; generic parser plus IDBank / Ameriabank / ACBA parsers; low-confidence results go to a confirmation screen. Rule-based `CategorizationEngine` (normalized hy/ru/en keywords, priority, user rules). CSV import with column mapping, run on a worker thread, deduplicated with the existing fingerprint + time window. |
| 3 – Budgets & analytics | Budget service with 80/90/100 % thresholds; charts drawn with Qt Quick (Shapes/Canvas), not Qt Charts (licensing and extra module on iOS); monthly series from SQL aggregates. |
| 4 – iOS native | Objective‑C++ behind C++ interfaces, same pattern as `PlatformServices`: `IBiometricAuth` (LocalAuthentication / Face ID), `ISecureStore` (Keychain), `INotificationScheduler` (UNUserNotificationCenter), `IDocumentPicker` (UIDocumentPickerViewController, security-scoped URLs). Desktop gets stubs so logic stays testable. `.ts` translations for en/hy/ru via `qt_add_translations`. |
| 5 – Hardening | Profiling on device, accessibility labels, performance with large histories, final deployment checklist. |

iOS gives no app access to the Messages database, and none is used. Bank SMS
reach the app through a user-created Shortcuts *Message* automation; see §9 and
[IOS_SMS_FEASIBILITY.md](IOS_SMS_FEASIBILITY.md). CSV import and a bank‑API
connector remain future options behind interfaces.

## 8. Known limitations (current state)

* iOS target unbuilt/untested (see §1). This includes the whole iOS side of the SMS import
  (Swift extension, App Group, URL handler, the Shortcuts automation).
* Bank SMS layouts are **synthetic**; no real IDBank/Ameriabank/ACBA message was available.
* Budgets and Analytics tabs are placeholders (Phase 3).
* Language setting currently drives number/date formatting and category names;
  full UI translation is Phase 4. Plural forms (`%n transaction(s)`) show the
  English fallback until translations exist.
* Category icons are emoji; verified only with a monochrome fallback font here.
* Dashboard shows the default currency as the headline and other currencies as
  separate chips; it deliberately does not convert.

## 9. Bank SMS import

Full report: [IOS_SMS_FEASIBILITY.md](IOS_SMS_FEASIBILITY.md). Diagram:
[sms_architecture.svg](sms_architecture.svg). User guide: [SHORTCUTS_SETUP.md](SHORTCUTS_SETUP.md).

```
Shortcuts "Import Bank SMS" (Swift App Intents extension, app not running)
   -> App Group inbox/<uuid>.json                (ios/IntentsExtension)
IBankTransactionReceiver  <-  DirectoryInboxReceiver  <-  IOSBankTransactionReceiver (.mm)
                                                      <-  DesktopBankTransactionReceiver
   -> SmsImportService::process()   sanitize -> identify bank -> parse -> duplicates -> account
                                    -> categorize -> store (one DB transaction) -> sms_imports row
```

* **Receivers** differ only in *where* envelopes are read from; platform code is compiled
  per platform (`Q_OS_IOS` in `ApplicationManager`, `IOSBankTransactionReceiver.mm` only in the iOS
  target). A source file is deleted only after the pipeline stored the outcome.
* **Parsers** implement `BankSmsParser` (`id`, `bankName`, `filterPhrases`, `matchScore`, `parse`).
  `TemplateSmsParser` turns one layout string per language into a regex and falls back to a
  bank-agnostic extractor (lower confidence). A new bank is one small class plus a registry line
  and, on iOS, one enum case in `BankChoice.swift`.
* **Confidence** is separate for parse (template 92, generic 62, minus penalties; below 60 → review)
  and category (rule confidence; below 70 → suggestion only). Nothing uncertain is applied silently.
* **Trust:** envelopes from the extension are trusted; `personalfinance://` URLs (any app can send
  them) are routed to review unless the user opts in. Text is sanitized, sizes are limited, secrets are
  dropped unread, card-number-like digit runs are masked before storage.
* **`ApplicationManager`** owns the services and receiver, drains the inbox when the app becomes active,
  and bumps `App.revision` so the monthly numbers, balances and the SMS screens refresh.
* **QML:** `SmsImportPage` (status, banks, setup, review, history, errors), `SmsReviewCard`,
  `ToggleSwitch`; reached from Settings → Bank SMS import.
